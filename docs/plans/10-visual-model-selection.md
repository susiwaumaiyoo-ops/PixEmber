# PixEmber Phase F「視覚モデル選定書」（承認ゲート）

> 目的: `visual_search_service.dart` の暫定 `ColorGridEncoder`（192 次元・色構成ベース）を、
> 本格的な ONNX 視覚エンコーダ（CLIP 系）へ置換するための**モデル選定・ライセンス分析・承認ゲート**を定める。
> 本ドキュメントは設計書。**コード変更・モデル組み込みは一切行わない。**
> 実装はユーザーの承認（本書末尾のゲート）を得てから別フェーズとして着手する。

---

## 0. 背景と現状（HEAD 確認）

- 視覚検索（`VisualEncoder` 抽象）は DI されており、エンコーダ差し替え時も
  DB スキーマ（`image_embeddings`、DB v20）・検索ロジックは変更不要。
- 現行 `ColorGridEncoder`: 8×8 セル平均 RGB = 192 次元。色合い・構図が近い画像を
  「大まかに」検索できるプレースホルダ。意味的類似（犬/猫、風景/室内等）は判定不可。
- ベクトル保管: `Float32` BLOB、`L2 正規化`、類似度はコサイン。
- ランタイム: `flutter_onnxruntime`（既存の Ruri v3 / reranker と同一）。
- 制約（共通ルールより）:
  - DB バージョンは順次更新（現在 v23）。本 Phase でスキーマ変更する場合は v24 へ。
  - モデル・画像バイナリはリポジトリに含めない（既存方針通り、ダウンロード配信）。
  - 非破壊的変更のみ。UI スレッドでの重い計算は禁止（Isolate.run は既存の通り使用可、
    ただしクロージャが Widget/Binding を参照しない純データのみ）。
  - 新規パッケージは原則追加しない（`flutter_onnxruntime` は既導入）。

## 1. 要件定義（置換に求められる性質）

1. `flutter_onnxruntime` で動作する ONNX（int8/int32/fp16 可）。
2. 画像 1 枚 → 固定次元 `Float32` ベクトル（L2 正規化想定）。
3. ライセンスが**商用アプリ（PixEmber は実質配布型）でも利用可能**であること。
4. 入力解像度がモバイル実行に現実的（224〜336px 級）。
5. 言語非依存（pixiv は日本語タグ中心だが視覚検索は画像のみで十分）。
6. 重みサイズがダウンロード配信に現実的（推奨 100MB 以下、許容 300MB 以下）。

## 3. ライセンス分析（最重要）

### 3.1 商用配布の可否
- **MIT / Apache-2.0**: 商用配布 OK。アプリへの組み込み・再配布（モデル本体のダウンロード配信）は
  ライセンス表示（NOTICE / コピーライト）を同梱すれば許容。
- **CC-BY-4.0**: 商用 OK だが**「帰属表示」が必須**。アプリ内設定画面等へ
  「モデル名・作者・ライセンス・URL」の表示が必要（既存 Ruri v3 の info.json 表示パターンを流用）。
- **CC-BY-NC / 非商用**: **使用不可**。PixEmber は事実上の配布型であるため除外。
- **OpenRAIL / 利用制限付き**: 出力用途制限等がありアプリ組み込みに不確実性。保留。

### 3.2 pixiv コンテンツとの関わり
- 本モデルは**ユーザー端末内のダウンロード済み画像**のみを入力とし、pixiv から
  モデル学習データを取るわけではない。よって学習データのライセンス論点は発生しない。
- 類似検索結果の「見せ方」は既存 `VisualSearchScreen` のまま（オフライン・ローカル完結）。

### 3.3 結論（暫定推奨）
- **V1: `openai/clip-vit-base-patch32` (int8 ONNX)** を第一候補とする。
  - 理由: MIT ライセンス（最も安全）、次元 512 で既存 `image_embeddings` 設計と整合、
    入力 224×224 でモバイル実行現実的、実績豊富。
  - ただし**実装着手前に以下を確定**する（ゲート参照）:
    1. Hugging Face での実在確認（URL/ファイル名/サイズ/SHA-256）。
    2. int8 ONNX の `flutter_onnxruntime` 動作検証（小規模プロトタイプ）。
    3. 出力次元 512 への `image_embeddings` 互換（既存 192 次元からの移行 or 別カラム）。

## 4. DB スキーマ影響（非破壊方針）

- 次元が 192 → 512 に変わる場合:
  - 既存 `image_embeddings.vector` BLOB は 192 次元固定。互換性のため
    **別カラム `vector_v2`（512 次元）を追加**し、旧データは遅延再生成（非破壊）。
  - または `model_id` カラムで互換判定（既存 Ruri の `model_id`/`version`/`prefix` パターン）。
- いずれにせよ **DB v23 → v24** の `_onUpgrade` で `PRAGMA table_info` ガード付き `ALTER TABLE` を追加。
- 元画像から再生成可能なため Google Drive バックアップ対象外（現状維持）。
